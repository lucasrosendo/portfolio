3:T1a1c,<h2>The Pitch</h2>
<p>The core idea is simple to say and hard to build: a card game where every character is defined by <strong>two fighting styles</strong> chosen from a roster of ten — boxing, wrestling, karate, BJJ, and others — each with its own authentic progression system (belts, weight-class records, win counts, time-and-test exams). Combat itself is turn-based, but with a twist: players can react to an opponent's declared move with an <strong>instant defense</strong>, paid for out of the same shared stamina pool they'll need for their own next turn.</p>
<p>That single design choice — ten <em>genuinely different</em> progression systems layered on top of a reactive combat loop — is also the project's single biggest technical risk. This devlog covers the first real pass at taming it: the architecture plan, the risks we flagged, and what a hand-run combat simulation already taught us before a single UI screen exists.</p>
<h2>Problem: Ten Progression Systems, One Codebase</h2>
<p>Belts don't work like weight-class records. Weight-class records don't work like win-count rankings. If we build each fighting style as its own bespoke system, we get ten times the code, ten times the bugs, and a UI team drowning in one-off screens.</p>
<h2>Technical Solution: Data-Driven Everything</h2>
<p>The architecture leans hard on Unity <code>ScriptableObject</code>s and the Strategy pattern to keep that variety from leaking into the codebase:</p>
<ul>
<li><strong><code>CardDefinition</code></strong> (ScriptableObject) holds a card's identity — id, style, type, stamina cost, rarity, minimum tier — but <em>not</em> a fixed effect field. Card effects (flat damage, conditional percentage buffs, damage reduction with a floor, flat reduction, opponent debuffs) are too varied for a single struct, so each card holds a list of polymorphic <code>CardEffect</code> objects (<code>DamageEffect</code>, <code>DamageMultiplierBuffEffect</code>, <code>PercentDamageReductionEffect</code>, and so on), each implementing <code>Apply(CombatContext ctx)</code>. New effect types slot in without touching <code>CardDefinition</code> itself.</li>
<li><strong><code>FightingStyleDefinition</code></strong> describes a style as an ordered list of <code>GradeDefinition</code>s (display name, unlocked card tier, build points, UI requirements) — so "Purple Belt," "Featherweight Contender," and "Level 3" are just data, not separate code paths.</li>
<li><strong><code>IGradeProgressionEvaluator</code></strong> is the piece that actually collapses the ten-systems problem: instead of ten bespoke advancement rules, we expect <strong>3-4 reusable archetypes</strong> — a win-count evaluator (wrestling-style), a time-and-test evaluator (karate/BJJ-style belts), and a record-by-weight-class evaluator (boxing-style) — each <code>FightingStyleDefinition</code> just references which one it uses.</li>
<li>Combat resolution is a <strong>State pattern with an observable interrupt point</strong>: <code>AwaitingAction → ActionDeclared → ReactionWindow → ResolvingEffects → TurnEnd</code>, with instant defense implemented as an observer that intercepts the <code>ActionDeclared → ResolvingEffects</code> transition. That interrupt point is also where multiplayer would eventually hook in, without rewriting the state machine.</li>
</ul>
<p>The first system slated for prototyping is deliberately unglamorous: a pure C# combat core (turn state machine + stamina + effect pipeline) with <strong>no <code>MonoBehaviour</code>, no <code>Update()</code></strong>, testable headlessly through Unity's Edit Mode Test Runner. UI comes after that core is proven stable, not before.</p>
<h2>Player Impact: What a Hand-Simulated Fight Already Found</h2>
<p>Before writing a line of gameplay code, we ran combat entirely on paper — four manual rounds, Fighter A always acting first — to sanity-check the core rules:</p>
<ul>
<li>Stamina caps at 5, regenerates +2 per own turn (capped, no overflow loss), with turn 1 as a fixed exception (both fighters start at 3).</li>
<li>Attacks, buffs/debuffs, <em>and</em> instant defense all draw from the same stamina pool.</li>
</ul>
<p><strong>Result:</strong> 70 HP (Fighter A) vs. 75 HP (Fighter B) — close, despite A having the theoretical first-move advantage. That's an encouraging early signal that shared stamina plus reactive defense is doing its job of neutralizing "whoever attacks first wins."</p>
<p>But the same four rounds surfaced two real problems worth fixing before this goes further:</p>
<ul>
<li><strong>The "empty turn" bug.</strong> Because instant defense spends from the <em>same</em> pool as a fighter's own upcoming action, it's possible to reach your turn with zero stamina and nothing playable — round 2 hit exactly this for Fighter B. A fully wasted turn doesn't feel good in a fighting game, so the fix under consideration is a guaranteed zero-cost card (a basic dodge or step-back, no damage) or a stamina floor that never bottoms out completely.</li>
<li><strong>A possible "reacts second" advantage.</strong> The fighter who reacts mid-opponent's-turn gets to see the opponent's card <em>and</em> may have stamina left over for their own attack afterward; the fighter who acts first tends to spend stamina on their own move and has less left to defend with. Four rounds isn't enough data to confirm this pattern — it needs to run at scale.</li>
</ul>
<p>Which points directly at the next milestone: an <strong>automated simulation harness</strong>. Four manual rounds prove the concept; answering "does reacting second actually win more often?" needs thousands of automated simulations, not a spreadsheet. The existing hand-traced rounds already double as a ready-made regression test for that harness once it exists.</p>
<h2>What's Still Open</h2>
<p>A few decisions are deliberately unresolved and will shape the technical scope by orders of magnitude — most importantly, whether competitive PvP needs to feel like a live match (real-time netcode, authoritative server, the reaction window seeing the opponent's card <em>live</em>) or can be asynchronous (both players commit blind, resolve simultaneously — a real change to the core "see and react" mechanic). That call has to land before any networked combat UI gets built, and it's the headline open question heading into the next devlog.</p>

<p>A ideia central é simples de descrever e difícil de construir: um jogo de cartas onde cada personagem é definido por <strong>duas modalidades de luta</strong> escolhidas entre dez — boxe, wrestling, karatê, BJJ e outras — cada uma com seu próprio sistema de progressão autêntico (faixas, recordes por categoria de peso, contagem de vitórias, exames de tempo-e-teste). O combate em si é por turnos, mas com uma reviravolta: os jogadores podem reagir à jogada declarada do oponente com uma <strong>defesa instantânea</strong>, paga com o mesmo pool de estamina compartilhado que vão precisar no próprio turno seguinte.</p>
<p>Essa única decisão de design — dez sistemas de progressão <em>genuinamente diferentes</em> sobrepostos a um loop de combate reativo — também é o maior risco técnico do projeto. Este devlog cobre a primeira passada real para domar isso: o plano de arquitetura, os riscos sinalizados e o que uma simulação manual de combate já ensinou antes de existir uma única tela de UI.</p>
<h2>Problema: Dez Sistemas de Progressão, Um Só Código-Base</h2>
<p>Faixas não funcionam como recordes por categoria de peso. Recordes por categoria de peso não funcionam como rankings por contagem de vitórias. Se construirmos cada estilo de luta como um sistema sob medida, temos dez vezes mais código, dez vezes mais bugs e uma equipe de UI afogada em telas feitas sob encomenda.</p>
<h2>Solução Técnica: Tudo Orientado a Dados</h2>
<p>A arquitetura se apoia fortemente em <code>ScriptableObject</code>s da Unity e no padrão Strategy para impedir que essa variedade vaze para o código:</p>
<ul>
<li><strong><code>CardDefinition</code></strong> (ScriptableObject) guarda a identidade de uma carta — id, estilo, tipo, custo de estamina, raridade, tier mínimo — mas <em>não</em> um campo de efeito fixo. Os efeitos das cartas (dano fixo, buffs percentuais condicionais, redução de dano com piso mínimo, redução fixa, debuffs no oponente) são variados demais para caber numa struct única, então cada carta guarda uma lista de objetos <code>CardEffect</code> polimórficos (<code>DamageEffect</code>, <code>DamageMultiplierBuffEffect</code>, <code>PercentDamageReductionEffect</code>, entre outros), cada um implementando <code>Apply(CombatContext ctx)</code>. Novos tipos de efeito entram sem tocar em <code>CardDefinition</code>.</li>
<li><strong><code>FightingStyleDefinition</code></strong> descreve um estilo como uma lista ordenada de <code>GradeDefinition</code>s (nome de exibição, tier de carta desbloqueado, pontos de build, requisitos de UI) — então "Faixa Roxa", "Peso Pena Contender" e "Nível 3" são só dados, não caminhos de código separados.</li>
<li><strong><code>IGradeProgressionEvaluator</code></strong> é a peça que de fato resolve o problema dos dez sistemas: em vez de dez regras de avanço sob medida, esperamos <strong>3-4 arquétipos reaproveitáveis</strong> — um avaliador por contagem de vitórias (estilo wrestling), um avaliador de tempo-e-teste (faixas estilo karatê/BJJ) e um avaliador de recorde por categoria de peso (estilo boxe) — cada <code>FightingStyleDefinition</code> só referencia qual avaliador usar.</li>
<li>A resolução de combate é um <strong>padrão State com um ponto de interrupção observável</strong>: <code>AwaitingAction → ActionDeclared → ReactionWindow → ResolvingEffects → TurnEnd</code>, com a defesa instantânea implementada como um observer que intercepta a transição <code>ActionDeclared → ResolvingEffects</code>. Esse ponto de interrupção também é onde o multiplayer eventualmente se encaixaria, sem reescrever a máquina de estados.</li>
</ul>
<p>O primeiro sistema previsto para prototipagem é propositalmente pouco glamouroso: um núcleo de combate em <strong>C# puro</strong> (máquina de estados de turno + estamina + pipeline de efeitos) <strong>sem <code>MonoBehaviour</code>, sem <code>Update()</code></strong>, testável de forma headless pelo Test Runner em Edit Mode da Unity. A UI vem depois desse núcleo provado estável, não antes.</p>
<h2>Impacto no Jogador: O Que uma Luta Simulada à Mão Já Revelou</h2>
<p>Antes de escrever uma linha de código de gameplay, rodamos o combate inteiramente no papel — quatro rodadas manuais, com o Lutador A sempre agindo primeiro — para validar as regras centrais:</p>
<ul>
<li>A estamina tem teto de 5, regenera +2 por turno próprio (com teto, sem perda de excedente), com o turno 1 como exceção fixa (os dois começam com 3).</li>
<li>Ataques, buffs/debuffs <em>e</em> defesa instantânea saem todos do mesmo pool de estamina.</li>
</ul>
<p><strong>Resultado:</strong> 70 HP (Lutador A) contra 75 HP (Lutador B) — próximo, apesar da vantagem teórica de A por agir primeiro. É um sinal inicial encorajador de que estamina compartilhada mais defesa reativa estão cumprindo o papel de neutralizar o "quem ataca primeiro vence".</p>
<p>Mas as mesmas quatro rodadas revelaram dois problemas reais que valem a pena corrigir antes de avançar:</p>
<ul>
<li><strong>O bug do "turno vazio".</strong> Como a defesa instantânea gasta do mesmo pool da própria ação futura do lutador, é possível chegar ao seu turno com estamina zerada e nada jogável — a rodada 2 caiu exatamente nisso para o Lutador B. Um turno totalmente perdido não é uma boa sensação num jogo de luta, então a correção em consideração é uma carta garantida de custo zero (uma esquiva básica ou um passo atrás, sem dano) ou um piso de estamina que nunca zera de vez.</li>
<li><strong>Uma possível vantagem de "quem reage por último".</strong> O lutador que reage no meio do turno do oponente já viu a carta do adversário e ainda pode sobrar estamina para o próprio ataque depois; quem age primeiro tende a gastar estamina no próprio golpe e sobra menos para se defender depois. Quatro rodadas não são suficientes para confirmar esse padrão — precisa rodar em escala.</li>
</ul>
<p>O que aponta direto para o próximo marco: um <strong>harness de simulação automatizada</strong>. Quatro rodadas manuais provam o conceito; responder "reagir em segundo realmente vence mais?" exige milhares de simulações automatizadas, não uma planilha. As rodadas já traçadas à mão já servem como um teste de regressão pronto para esse harness assim que ele existir.</p>
<h2>O Que Ainda Está em Aberto</h2>
<p>Algumas decisões estão propositalmente em aberto e vão mudar o escopo técnico em ordens de grandeza — a mais importante: se o PvP competitivo precisa parecer uma partida ao vivo (netcode em tempo real, servidor autoritativo, a janela de reação vendo a carta do oponente ao vivo) ou pode ser assíncrono (os dois jogadores comitam às cegas, resolvendo simultaneamente — uma mudança real na mecânica central de "ver e reagir"). Essa decisão precisa ser tomada antes de qualquer UI de combate em rede ser construída, e é a pergunta em destaque para o próximo devlog.</p>
